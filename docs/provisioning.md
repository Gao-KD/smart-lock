# 出厂状态、绑定注册与恢复出厂

本文定义门锁从出厂到投入使用、再到退役或返修的全生命周期：出厂时写入什么、未绑定时怎么开门、网关批量绑定和安装师傅蓝牙绑定怎么走、绑定过程中断电或断连怎么保证门锁不变砖、怎么恢复出厂。硬件要配合的部分见 [hardware/handoff.md](hardware/handoff.md)。

设计目标只有一条：**任何时刻断电、断连、重启，门锁要么还是旧状态，要么已经是完整的新状态，并且平台始终有办法把它找回来。**

## 1. 参考涂鸦的做法，以及我们的差异

涂鸦等家用智能设备平台的公开做法（以其官方文档为准）大致是：

| 涂鸦的做法 | 本项目怎么借鉴 |
| --- | --- |
| 每台设备出厂烧录唯一授权（UUID + AuthKey），云端预先登记 | 每把锁出厂注入唯一 `K_dev`，EUI + `K_dev` 加密导入平台密钥服务（第 2 节） |
| 设备未配网时进入“配网模式”，有时间窗口（约 3 分钟），超时退出；长按复位键重新进入 | 未绑定的锁在上电和按设置键后的窗口内主动请求入网/广播，超时退避（第 4 节） |
| App 经蓝牙把配网信息交给设备，设备再向云端“激活”，激活后得到通信密钥 | 安装师傅 App 只做透明转发，密钥由平台用 `K_dev` 加密下发，App 看不到（第 5.2 节） |
| 在 App 里“移除设备”或设备本地复位，解除绑定，回到配网模式 | 平台解绑 / 室内设置键 + 授权才能复位（第 6 节） |
| 门锁类产品：未添加管理员前，任意指纹等可开门（行业常见的“体验模式”） | 未绑定时 123456、任意卡、任意指纹、任意人脸能开（第 3 节） |

差异：涂鸦面向一户一锁、用户自己配网；本项目面向一栋楼几百把锁、由平台统一管理，所以增加了**网关批量绑定**、**绑定事务（两阶段提交）**、**永久恢复根密钥**，以及**复位必须授权**（防止学生在室内按复位键把锁变成“任意卡可开”）。

## 2. 出厂时写入什么

### 2.1 产测工位写入的内容

| 内容 | 存放 | 说明 |
| --- | --- | --- |
| EUI-64 | 芯片自带 | 门锁唯一地址 |
| `K_dev`（128 位，随机） | Secure Vault 持久密钥，**不可导出、不随复位擦除** | 设备根密钥：只用于入网认证和加密下发绑定密钥（派生出 `K_join`、`K_wrap`，见 5.4） |
| 出厂标志 `MFG_DONE`、硬件版本、产测结果 | NVM3（只写一次的对象） | |
| 绑定状态 `BIND_STATE = FACTORY` | NVM3 | 见第 4 节状态机 |
| 固件签名公钥 | Bootloader 内 | 只接受签名固件，防止刷掉绑定逻辑 |
| 调试口锁定 | Secure Vault 调试锁 | 量产板锁 SWD，防止读密钥 |

产测脚本把 `(EUI, K_dev)` 用平台密钥服务的公钥加密后上传或导出成文件，平台导入后这把锁才“存在”。**产测数据库就是这把锁的出生证明，必须备份**：丢了 `K_dev`，锁就只能返厂。

### 2.2 锁体标签

二维码内容：`EUI | 型号 | 硬件版本 | 6 位校验码`。校验码 = 对 EUI 的 MAC（用 `K_dev` 派生），只用于确认“扫到的码属于眼前这把锁”，**不含任何密钥**。标签贴在锁体内侧和包装盒上各一张，安装时可以先扫码再装。

## 3. 未绑定状态（体验/安装模式）

| 项 | 行为 |
| --- | --- |
| 开门 | 键盘输入 `123456#`、刷任意 13.56 MHz 卡、按任意手指、任意人脸都能开；手机蓝牙不需要令牌 |
| 提示 | 每次开门后蓝灯快闪 + 语音/提示音“门锁未绑定”，提醒安装人员 |
| 记录 | 开门记录照常写日志，绑定后作为“未绑定期间记录”上报一次 |
| 联网 | 见第 4 节：在入网窗口内向网关发“未绑定入网请求”；BLE 广播带“未绑定”标志 |
| 不允许 | 远程开门、下发凭证（必须先绑定拿到 `K_app`）；本地录入任何凭证 |
| 运输模式（可选） | 产测最后一步可以设为“运输模式”：射频和 BLE 全关，第一次有人碰键盘或按设置键才退出，避免仓库里几千把锁一直发入网请求耗电 |

绑定提交成功的瞬间（4.2 节第 ⑤ 步）体验模式关闭：123456、任意卡、任意指纹人脸全部失效，只认平台下发的凭证。

## 4. 绑定状态机

### 4.1 门锁上的持久状态

NVM3 里有三类对象，每个对象自带 CRC，NVM3 单对象写入是原子的（掉电时要么是旧值，要么是新值）。

| 对象 | 内容 |
| --- | --- |
| `BIND_STATE` | `state`、`active_slot`（0/1）、`txn_id`、`epoch`、`pending_since` |
| `KEYSLOT[0]`、`KEYSLOT[1]` | 每个槽：`epoch`、`txn_id`、租户号、楼栋/房间号、网关 PAN、`KCV`（密钥校验值）；对应的 `K_link`、`K_app`、`K_grp` 作为 PSA 持久密钥存在 Secure Vault，密钥 ID 按槽号固定（例如槽 0 用 0x100–0x10F，槽 1 用 0x110–0x11F） |
| 凭证库、配置、日志 | 已有，见 lock-features.md |

`state` 取值：

| 状态 | 含义 | 开门规则 | 用哪组密钥通信 |
| --- | --- | --- | --- |
| `FACTORY` | 出厂/已复位，从未绑定 | 体验模式 | `K_dev` 派生密钥 |
| `STAGED` | 已收到并存好新密钥（暂存槽），未提交 | 仍是体验模式（或绑定前的旧状态） | 收：`K_dev` 和暂存密钥都能验；发：`K_dev` |
| `BOUND` | 正常使用 | 只认平台凭证 | 活动槽密钥 |
| `BOUND + STAGED` | 已绑定，正在换密钥（换房间、换租户、密钥轮换） | 照旧用活动槽 | 活动槽；暂存槽仅用于验证提交指令 |

### 4.2 两阶段提交（网关和蓝牙绑定共用）

```
  平台/KMS                          中继（网关 或 安装 App）              门锁
     │ ① 生成新密钥 epoch=n+1           │                                  │
     │   记为 PENDING，旧密钥保留       │                                  │
     │── BIND_PREPARE ─────────────────▶│─────────────────────────────────▶│ ② 写暂存槽（非活动槽）
     │   (txn, 密钥用 K_wrap 加密,       │                                  │   先写密钥再写 BIND_STATE=STAGED
     │    房间/网关信息, 有效期)          │                                  │
     │◀──────────────── PREPARED(txn, KCV) ◀──────────────────────────────│ ③ 用新 K_app 算 KCV，K_dev 认证
     │ ④ 校验 KCV = 门锁确实拿到了正确密钥 │                                  │
     │── BIND_COMMIT(txn) ─────────────▶│─────────────────────────────────▶│ ⑤ 用暂存的新 K_app 验证
     │   用【新 K_app】认证              │                                  │   一次原子写 BIND_STATE：
     │                                  │                                  │   state=BOUND, active_slot=新槽
     │◀──────────────── COMMITTED(txn) ◀──────────────────────────────────│ ⑥ 用新密钥发；关闭体验模式
     │ ⑦ 标记 BOUND，旧密钥作废           │                                  │   之后以新 K_link 正常入网
```

每一步的含义：

- **② 写暂存槽**：只写非活动槽，活动槽（如果有）完全不动。顺序是先删暂存槽旧密钥 → 导入新密钥 → 写 `KEYSLOT[新槽]` 元数据 → 最后写 `BIND_STATE=STAGED`。任何一步掉电，重启后发现 `BIND_STATE` 没变或槽 CRC 不对，就当作没收到，等平台重发。
- **③ PREPARED 带 KCV**：`KCV = MAC(新 K_app, "KCV" | txn)` 的前 8 字节。平台核对后才知道门锁存下的密钥和自己的一致（防止传输错误、存储损坏）。
- **④ 提交指令用新密钥认证**：证明发指令的一方确实持有新密钥；同时门锁验证成功也再次证明自己存储的密钥可用。
- **⑤ 提交是一次原子写**：切换活动槽只改 `BIND_STATE` 一个对象。这是整个流程唯一的“切换点”。
- **⑦ 平台确认**：平台收到 `COMMITTED`，或者收到任何一条用新密钥通过认证的上行（例如重连心跳），就把锁标记为 `BOUND` 并删除旧密钥。在此之前平台**两组密钥都保留**，用哪组能验过就按哪组处理。

### 4.3 断电 / 断连恢复表

| 中断点 | 门锁重启后状态 | 平台状态 | 怎么继续 |
| --- | --- | --- | --- |
| ② 之前（PREPARE 没收到或写一半） | 旧状态（FACTORY 或原 BOUND） | PENDING | 平台超时重发同一个 PREPARE（同一 txn、同一密钥） |
| ② 之后、③ 没送达 | STAGED | PENDING | 门锁入网请求里带 `staged_txn`；平台重发同一 txn 的 PREPARE，门锁发现已存好就不重写，直接回 PREPARED，然后继续 ④ |
| ③ 之后、⑤ 之前 | STAGED | PREPARED | 平台重发 COMMIT（幂等） |
| ⑤ 之后、⑥ 没送达 | BOUND（新） | PREPARED | 门锁用新 `K_link` 入网 + 发“绑定完成”心跳，平台据此进入 ⑦；平台重发的 COMMIT 门锁直接回 COMMITTED |
| ⑦ 前平台宕机 | BOUND（新） | PREPARED（持久化） | 平台恢复后按两组密钥验上行，自动完成 ⑦ |
| 长时间停在 STAGED | STAGED | PENDING/PREPARED | 平台 7 天未完成就发 `BIND_ABORT`（`K_dev` 认证），门锁清空暂存槽回旧状态；门锁自己**不**主动丢弃暂存槽，避免平台已认为提交时门锁回滚 |
| 门锁 STAGED 时收到另一个 txn 的 PREPARE | — | — | 新 txn 覆盖暂存槽（只有平台能用 `K_dev` 加密下发，旧 txn 自动作废） |

规则汇总：

1. **活动密钥在新密钥被双方证实之前绝不删除。** 门锁靠 A/B 槽，平台靠“两组都保留”。
2. **每个消息都幂等。** 同一 txn 的 PREPARE/COMMIT 重复收到只回同样的结果。
3. **门锁不自己回滚已经 STAGED 的事务**，回滚只由平台的 `BIND_ABORT` 触发，所以不会出现“平台以为绑好了、门锁却退回去了”。
4. **`K_dev` 永远不擦除。** 不管门锁处于什么状态、活动槽密钥是否损坏，平台都可以用 `K_dev` 认证的 `BIND_ABORT` / `FACTORY_RESET` / 新的 `BIND_PREPARE` 把它拉回来——这是“不会变砖”的根本保证。

### 4.4 提交时的硬件保护

绑定过程会写 Secure Vault 和 NVM3，最怕写到一半电压塌掉：

- 进入 ② 和 ⑤ 之前检查电池电压，低于“低电”阈值（例如 4.6 V，4×AA）拒绝，回复 `LOW_BATTERY`，安装 App 提示换电池或插 USB-C 应急电源。
- 绑定事务进行中禁止驱动电机（电机启动电流最大），开门请求排队到提交结束。
- 打开 EFR32 的欠压检测（BOD），并在 NVM3 写入前确认电压；主板 3.3 V 上的储能电容要保证一次最长的 NVM3 写入 + 页擦除能完成（硬件同事按数据手册的写入时间核算）。
- 看门狗复位、软件异常都等同于掉电，用同一套恢复逻辑。

## 5. 两种绑定方式

### 5.1 网关批量绑定（推荐用于整栋楼）

前提：门锁 EUI 和房间号的对应关系已知，来源任选：

- 安装时师傅用 App 扫锁体二维码 + 选房间（只扫码，不需要蓝牙操作，最快）；
- 工厂按发货单把 EUI 和房间预先对应，装锁时按箱号对号入座；
- 先装后认：先让所有锁入网，平台显示“未分配的锁”及其 RSSI 和所在网关，宿管在楼层图上拖拽对应（适合少量）。

流程：

1. 平台为每台网关创建“绑定任务”：允许绑定的 EUI 列表 + 每个 EUI 的房间。
2. 装上电池（或按任意键）后，`FACTORY` 门锁在入网窗口内发 `JOIN_REQ(unbound)`，用 `K_join` 算 MIC。窗口：上电后 10 分钟内按 3 s、6 s、12 s… 退避；之后每小时一次；按设置键或键盘重新打开 10 分钟窗口。
3. 网关把入网请求转给平台；平台用 KMS 校验 MIC，确认 EUI 在本网关的绑定任务里，才给它分配临时地址和时隙。**不在列表里的锁不绑定**，只在平台上显示为“发现未知锁”，防止把隔壁楼的锁绑错。
4. 网关在该锁的时隙里依次下发 PREPARE、COMMIT（第 4.2 节）。每把锁 3 个来回，按每秒一个周期大约 3–5 秒；同一网关下几百把锁分布在不同时隙并行进行，一台网关下全部锁通常 1–2 分钟内完成。
5. 提交后门锁用新 `K_link` 正常入网，平台把房间设为“已绑定、在线”，可以下发凭证。
6. 绑定失败（电压低、信号差、超时）的锁在平台上列出原因，安装师傅到场用蓝牙补绑。

### 5.2 安装师傅蓝牙绑定（单把、补绑、网关还没装好时）

1. 师傅登录安装 App，拿到自己的工单（楼栋、房间列表）。
2. 到门口，**按室内设置键**（或在键盘输入 `123456#` 后长按 `*` 3 秒），门锁蓝灯闪烁并开始 BLE 广播 3 分钟，广播里带：EUI、绑定状态、电量、`staged_txn`（如果有）。只有物理触发后才可连接，防止 App 连错隔壁门。
3. App 扫描并匹配（也可以扫锁体二维码直接定位 EUI），选房间，向平台请求该锁的绑定包。
4. 平台生成 PREPARE（密钥用 `K_wrap` 加密），App 经 BLE 原样转发；门锁回的 PREPARED 再原样转给平台；平台回 COMMIT，App 转发；门锁回 COMMITTED。**App 全程只是管道，看不到任何密钥**，和网关的角色完全一样。
5. 最后一步：门锁用新密钥经 PAwR 向楼层网关入网，App 显示入网结果和 RSSI（从平台取，或门锁经 BLE 报告），师傅确认“信号合格”再离开。网关还没装的楼，这一步标记为“待入网”，网关上线后自动完成。

**手机没网络时（地下室、新楼没信号）**：App 在有网时预先下载工单内每把锁的 PREPARE 和 COMMIT（COMMIT 用新 `K_app` 预先签好，平台能提前算）。现场离线完成 4.2 节的 ②~⑥，App 缓存门锁返回的 PREPARED/COMMITTED，回到有网的地方再上传；平台在收到回执或该锁第一条新密钥上行时完成 ⑦。预下载的包有有效期（例如 72 小时），过期作废。

**BLE 断连**：连接监督超时设 6 秒；断开后 App 自动重连并从门锁读当前 `BIND_STATE` 和 `staged_txn`，按 4.3 节表格续做，不会从头开始，也不会重复写入。

### 5.3 换房间、换租户、密钥轮换

已绑定的锁走同一个两阶段提交，区别只是 PREPARE 用旧 `K_app` 加密（也可以用 `K_dev`），门锁处于 `BOUND + STAGED` 期间一切照常工作。毕业季整栋楼换租户 = 批量密钥轮换 + 清空凭证，两者都可以经网关批量完成。

### 5.4 密钥关系

| 密钥 | 来源 | 用途 |
| --- | --- | --- |
| `K_dev` | 出厂随机，永久 | 只做派生，不直接加密业务数据 |
| `K_join = KDF(K_dev, "JOIN")` | 派生 | 入网请求 MIC、平台认证的 ABORT/RESET 指令 |
| `K_wrap = KDF(K_dev, "WRAP" \| epoch)` | 派生 | 加密下发新密钥（PREPARE 里的密钥字段） |
| `K_link`、`K_app`、`K_grp` | 平台 KMS 每次绑定随机生成 | 正常通信，见 README 和 secure.h；**不再由 `K_dev` 直接派生**，所以解绑后旧租户的密钥彻底失效 |

KDF 在 EFR32 上用 PSA 的 HKDF（或 AES-CMAC KDF），派生结果作为易失密钥只在 Secure Vault 内存在。

## 6. 恢复出厂与解绑

宿舍场景的威胁是：住户在室内按复位键，锁回到体验模式，任何人都能刷卡进来。所以**已绑定的锁不允许仅凭本地按键恢复出厂**。

| 方式 | 条件 | 结果 |
| --- | --- | --- |
| 平台远程解绑 | 宿管在平台操作，下发 `UNBIND`（`K_app` 认证） | 门锁清空凭证、删除活动槽密钥 → `FACTORY` |
| 平台强制恢复 | 活动密钥损坏、平台数据丢失只剩 `K_dev` 时；下发 `FACTORY_RESET`（`K_join` 认证），经网关或经安装 App 转发 | → `FACTORY` |
| 本地 + 授权 | 按室内设置键 10 秒 → 门锁进入“复位待授权”3 分钟并 BLE 广播；安装 App 向平台申请一次性复位授权（平台记录谁、何时、哪把锁）并转发 | → `FACTORY` |
| 本地 + 离线复位码 | 网络不可用时，平台签发一个“复位码”（离线密码种类 8，算法同离线密码，用 `K_app`），在键盘输入 | → `FACTORY` |
| 未授权的本地长按 | 只按设置键，没有授权 | **不复位**，上报“复位尝试”告警；只重新打开 BLE 广播窗口用于维护 |
| 未绑定的锁 | `FACTORY` 或 `STAGED` 时长按设置键 10 秒 | 直接清空暂存槽和体验期记录，仍是 `FACTORY`（不涉及安全问题） |
| 返厂 | 以上都不可用（`K_dev` 记录丢失） | 产测工位重新注入 `K_dev`（需要解除调试锁的厂内流程） |

恢复出厂只清空：活动槽和暂存槽密钥、凭证库、配置（回默认）、日志（先尽量上报）。**不清空：`K_dev`、EUI、出厂标志、固件。**

## 7. 需要新增的协议消息

在现有 MAC 命令（`JOIN_REQ`、`JOIN_ACCEPT`）和应用命令之外新增（编号待软件实现时定，此处为建议）：

| 消息 | 方向 | 认证 | 主要字段 |
| --- | --- | --- | --- |
| `JOIN_REQ`（扩展） | 锁 → 网关 | `K_join`（未绑定）/ `K_link`（已绑定） | 新增 `bind_state`、`staged_txn`、`epoch`、电压 |
| `BIND_PREPARE` | 平台 → 锁 | `K_dev` 派生（未绑定）或旧 `K_app` | `txn`、`epoch`、加密的 `K_link/K_app/K_grp`、租户/房间、网关 PAN、有效期 |
| `BIND_PREPARED` | 锁 → 平台 | `K_join` | `txn`、`KCV`、结果码（`OK`/`LOW_BATTERY`/`BAD_PARAM`/`HW_FAULT`） |
| `BIND_COMMIT` | 平台 → 锁 | 新 `K_app` | `txn` |
| `BIND_COMMITTED` | 锁 → 平台 | 新 `K_app` | `txn`、未绑定期间开门记录数 |
| `BIND_ABORT` | 平台 → 锁 | `K_join` | `txn` |
| `UNBIND` | 平台 → 锁 | `K_app` | 原因 |
| `FACTORY_RESET` | 平台 → 锁 | `K_join` | 授权号、有效期（防重放用单调递增授权号，门锁记录最大值） |
| `EVT_RESET_ATTEMPT` | 锁 → 平台 | `K_app` | 未授权长按告警 |

经 BLE 时这些消息原样装进一个 GATT 特征值透传（写 + 通知），BLE 层另做配对，但安全性不依赖 BLE 配对。

## 8. 联调测试用例（硬件和软件一起跑）

| # | 用例 | 预期 |
| --- | --- | --- |
| 1 | 新锁上电，123456、任意卡、任意指纹/人脸开门 | 能开，提示“未绑定” |
| 2 | 网关批量绑定 1 把 / 一层楼 | 全部 BOUND，体验模式关闭 |
| 3 | ② 写入过程中断电（用可编程电源在收到 PREPARE 后 0–50 ms 随机断电，重复 200 次） | 每次重启都是 FACTORY 或 STAGED，没有损坏；最终都能绑上 |
| 4 | ⑤ 提交时断电（同上，200 次） | 每次重启都是 STAGED 或 BOUND，且平台最终一致 |
| 5 | COMMITTED 丢失（网关丢弃该帧） | 门锁重新入网后平台自动确认 |
| 6 | 蓝牙绑定中途关掉手机蓝牙 / 走出范围 | 重连后从断点续做 |
| 7 | 手机离线绑定，24 小时后上传回执 | 平台确认 BOUND |
| 8 | 低电量（4.4 V）绑定 | 拒绝，返回 `LOW_BATTERY`，状态不变 |
| 9 | 已绑定锁长按室内设置键无授权 | 不复位，平台收到复位尝试告警 |
| 10 | 已绑定锁平台强制恢复（模拟活动槽损坏） | 回到 FACTORY，可重新绑定 |
| 11 | 绑定列表外的锁出现在网关下 | 不绑定，平台显示“未知锁” |
| 12 | 换房间（BOUND → 新密钥） | 期间开门不受影响，切换后旧密钥指令被拒 |

用例 3、4 是这套设计的核心验收，硬件同事需要一个能被脚本控制的电源（或继电器断电）来做。
